# Contributing to zenith-api

Thanks for helping build Zenith. This file gets you from a cold clone to a useful pull request in a day, even if you have never touched Stellar. Read it in order.

## What this repository is, and the other two

Zenith is a non-custodial crypto checkout on Stellar. A merchant creates an invoice, a customer pays it in USDC (or XLM on Testnet), and the money lands directly in the merchant's own Stellar account. Zenith never holds funds.

It ships as three repositories:

- **zenith-api** (you are here) — the REST API, invoice state machine, muxed address derivation, payment watcher, and webhook dispatcher. It owns the OpenAPI document and the webhook event catalogue.
- **[zenith-sdk](https://github.com/Elizabethxxx/zenith-sdk)** — the TypeScript client, generated from this repo's `openapi.json` and hand-wrapped.
- **[zenith-web](https://github.com/Elizabethxxx/zenith-web)** — the Next.js checkout page and merchant dashboard, which talk to the API only through the SDK.

Dependencies point one way: api, then sdk, then web, never reversed. A change in the API can require changes downstream; a change in the app never dictates the API. The cross-repository rules are in [docs/multi-repo.md](docs/multi-repo.md).

## The domain in two minutes

Four ideas are enough to work here.

A **Stellar account** is identified by a public key starting with `G`. It holds balances and receives payments. The merchant has one; Zenith holds no key for it.

A **muxed account** is a base account plus a 64-bit id, encoded together into an address starting with `M`. A payment to an `M` address arrives in the underlying `G` account with the id attached. Zenith gives every invoice its own muxed address derived from the merchant account and the invoice id, so a single account can tell its invoices apart with no contract and no pooled wallet. This is the whole non-custody story.

**Stroops** are the integer unit of a Stellar amount: one unit of an asset is 10,000,000 stroops. Every amount in this codebase is an integer count of stroops carried as a decimal string. A JavaScript float never touches a money path.

**Horizon** is Stellar's HTTP API. The watcher streams an account's payments from Horizon and reacts to them.

`docs/architecture.md` describes how the pieces fit, and the code follows it.

## Repository map

```
src/
  env.ts               environment parsing; refuses to start against mainnet
  index.ts             API entry point
  auth/apiKey.ts       API key generation, hashing, authentication
  db/
    schema.ts          Drizzle table definitions (the data model)
    client.ts          pooled Postgres client
    migrate.ts         apply migrations
    seed.ts            create and fund a demo merchant, print its API key
  http/
    app.ts             all routes; OpenAPI document is generated from here
    schemas.ts         zod request/response schemas
    serialize.ts       database rows to API shapes
    idempotency.ts     Idempotency-Key storage and lookup
  invoice/
    stateMachine.ts    allowed invoice transitions (pure, unit-tested)
    service.ts         create and cancel invoices
  watcher/
    index.ts           Horizon streaming loop, one stream per merchant
    process.ts         handle one payment; idempotent
    cursor.ts          persisted paging cursor
  webhooks/
    queue.ts           BullMQ queue and retry schedule
    worker.ts          delivery worker: sign, POST, record, retry
  events/
    emit.ts            enqueue webhooks, publish SSE updates
    types.ts           event catalogue
  lib/
    money.ts           stroop arithmetic, no floats
    hmac.ts            webhook signing
    redis.ts           Redis connections
    stellar/muxed.ts   derive and parse muxed addresses
  migrations/          generated by drizzle-kit; regenerate with `pnpm db:generate`
scripts/pay-demo.ts    end-to-end local proof
openapi.json           generated; regenerate with `pnpm openapi:emit`
```

The `src/migrations` directory and `openapi.json` are generated. Do not hand-edit them; run the regeneration command and commit the output.

## Getting set up

Prerequisites:

- Node 20 or newer
- pnpm 9 (`corepack enable`)
- Docker, for local Postgres and Redis

You do not need to deploy anything of your own. The seed script creates and funds a Testnet account for you with Friendbot, so there is no key to obtain by hand.

```bash
git clone https://github.com/Elizabethxxx/zenith-api
cd zenith-api
pnpm install
cp .env.example .env
docker compose up -d          # Postgres and Redis
pnpm db:migrate               # apply the schema
pnpm seed                     # prints a demo merchant API key
```

Run the three processes, each in its own terminal:

```bash
pnpm dev                      # API on http://localhost:8787
pnpm worker                   # webhook delivery worker
pnpm watcher                  # Horizon payment watcher
```

Now prove the whole loop, using the API key the seed printed:

```bash
ZENITH_API_KEY=zk_test_... pnpm tsx scripts/pay-demo.ts
```

It creates an invoice, pays it from a fresh Testnet account, and you will see the invoice flip to paid in the API log and a webhook attempt in the worker log. If that runs, your setup works.

To check the code without running the stack:

```bash
pnpm test                     # unit tests, no database or network needed
```

## Where to start

Issues carry one of three difficulty labels: `good first issue`, `intermediate`, `advanced`. The full list with acceptance criteria is in [ISSUES.md](ISSUES.md); here it is ordered easiest to hardest so you can pick a rung.

1. **API key scopes** (`good first issue`). Add read-only versus read-write scopes to keys. Touches `src/auth` and the route middleware. See PRD section 5.
2. **Invoice expiry sweeper** (`intermediate`). A job that moves lapsed invoices to `expired` and emits the event. Touches the state machine and a new periodic process. PRD section 4.4.
3. **Underpaid top-up flow** (`intermediate`). Expose how much is left on an underpaid invoice. Touches `src/invoice` and the watcher. PRD section 9.
4. **Overpayment credit** (`intermediate`). Record surplus as a credit rather than refunding. PRD section 9.
5. **Rate limiting** (`intermediate`). Per-key Redis limiter with standard headers.
6. **Audit log** (`intermediate`). Append-only record of sensitive actions.
7. **Watcher scaling** (`intermediate`). Shard accounts across workers with a lease. `src/watcher`.
8. **Soroban invoice-vault contract** (`advanced`). Vault mode: a per-merchant contract in `contracts/`. PRD section 4.2.
9. **Payment splits** (`advanced`). Split a paid invoice by basis points. Depends on the vault.
10. **On-chain refunds** (`advanced`). `refund` plus the `refund.created` event. Depends on the vault.
11. **Anchor settlement to fiat** (`advanced`). This is the single largest unclaimed piece: SEP-10 authentication, SEP-24 withdrawal, settlement rows, and a pluggable `Anchor` interface. PRD section 4.3.
12. **Mainnet configuration** (`advanced`). Gate mainnet behind explicit reviewed configuration without removing the guard.

To claim an issue, comment on it so two people do not build the same thing. For the vault contract, refunds, or the mainnet guard, open a discussion first: they change trust boundaries and want agreement before code.

## Rules that matter here

A reviewer will send a pull request back for any of these.

**Never take custody of funds.** No pooled account, no hot wallet, not in production and not in tests. Funds move from customer to merchant account directly. If a change makes funds pass through anything Zenith holds a key to, it is wrong regardless of convenience.

**Amounts are integer stroops, never a float.** Use the helpers in `src/lib/money.ts`. A `number` in a money path, or a `parseFloat` on an amount, does not merge.

**Every write path is idempotent.** The watcher will see the same Horizon payment more than once, and clients retry. Guard writes with unique keys, as `payments.horizon_operation_id` does, so a repeat is a no-op rather than a double-credit.

**Persist the Horizon cursor before side effects settle.** The watcher must resume without missing or replaying payments across a restart. Do not reorder the cursor save in a way that could skip an unhandled operation.

**No endpoint asks a user for a Stellar secret key.** The API never receives, stores, or logs a secret key. The only secret it stores is a webhook signing secret and an API key hash.

## Code style

TypeScript throughout, ES modules, Node 20. Formatting and linting are ESLint; there is no separate formatter step. Commits follow [Conventional Commits](https://www.conventionalcommits.org): `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`. Branch names like `feat/invoice-expiry` or `fix/watcher-cursor`.

CI runs exactly these, and they must pass:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm db:check      # migrations match the schema
```

Run them locally before pushing. Small pull requests get reviewed faster than large ones.

## Pull request checklist

- [ ] Branch off `main`, Conventional Commit messages.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` all pass.
- [ ] Schema changed? `pnpm db:generate` run and the migration committed; `pnpm db:check` passes.
- [ ] Routes changed? `pnpm openapi:emit` run and `openapi.json` committed.
- [ ] New behaviour has tests. Watcher or money changes especially.
- [ ] No secret key is ever received, stored, or logged.
- [ ] The description names which invariant, if any, the change touches.
- [ ] If this needs a matching change in zenith-sdk or zenith-web, that pull request is linked here.

## Releases

Maintainers cut releases. A release is a git tag `v0.x.y`; the tag is what the SDK's compatibility table points at. A tag builds and publishes the artifacts and republishes `openapi.json` as the frozen contract for that version. Do not bump versions or edit `deployments/` in a feature pull request; those belong to the release.

## Security

Report vulnerabilities privately per [SECURITY.md](SECURITY.md), never in a public issue. The sensitive surfaces here are muxed address derivation, API key handling, webhook signing, the payment watcher's idempotency, and the mainnet guard. Zenith is unaudited and Testnet-only.

## Community

Design discussion happens in this repository's GitHub Discussions. Protocol-level changes (the vault contract, the event catalogue, the API contract) need a written proposal there and one maintainer sign-off before implementation. Two merged pull requests earn triage rights on request. Commit rights on the API are granted slowly and after review work, because a bad change here can misdirect a payment; the web app grants them more readily.
